# AWS Terraform Drift Reconciler Test

Terraform examples and test scopes for preparing AWS state and IAM access, and
for exercising drift-reconciliation workflows. This repository contains
separate Terraform roots; initialize and run Terraform from the directory for
the stack you intend to manage.

## Repository layout

| Directory | Purpose |
| --- | --- |
| [`backend-state/`](./backend-state/) | Creates the shared S3 state bucket and DynamoDB lock table. This root uses local state. |
| [`bootstrap-customer/`](./bootstrap-customer/) | Creates customer-side scan and apply roles trusted by a configured backend role. |
| [`account-permissions/`](./account-permissions/) | Creates the backend identity, GitHub OIDC trust, scan/apply roles, and EC2 backend role in the automation account. |
| [`infra-test/`](./infra-test/) | Registry and preflight check for independent Terraform test scopes. |
| [`infra-test/lambda/`](./infra-test/lambda/) | Small Lambda deployment smoke test. |
| [`infra-test/multi-f/`](./infra-test/multi-f/) | Modular private-network Lambda, API, storage, and optional custom-domain test stack. |

## Suggested setup order

1. Review and apply `backend-state/` to create the remote-state bucket and lock
   table. Keep this root's state safe; it is stored locally by default.
2. Configure and apply `account-permissions/` in the automation account.
   Configure its OIDC-provider variables to use the account's existing provider
   or create one only if none exists.
3. Configure and apply `bootstrap-customer/` in the target customer account,
   using the correct backend role ARN and state resources.
4. Run the preflight check in `infra-test/`, then use either test scope
   independently.

The setup order may differ for an existing deployment. Confirm the AWS account,
credentials/profile, region, role trust, and Terraform plan before applying any
stack.

## Requirements

- Terraform and AWS CLI installed and available on `PATH`.
- AWS credentials with only the permissions required for the stack being
  managed. Configure the AWS CLI profile or environment before running
  Terraform.
- For the S3-backed roots, Terraform 1.10 or later (the backend configuration
  uses the S3 lockfile feature).
- A registered and delegated domain only if enabling the `multi-f` custom
  domain.

## General workflow

From the directory of the desired root:

```sh
terraform init
terraform validate
terraform plan
terraform apply
```

Inspect the plan and confirm the AWS account before applying. When a test is
complete, remove test resources with `terraform destroy` from the same root,
after reviewing its plan. Do not destroy shared backend or IAM infrastructure
as part of cleaning up a test scope.

## Multi-f apply-role trust

The multi-f apply role trusts the automation account root principal and limits
backend-user access with an `aws:PrincipalArn` condition in
[`infra-test/multi-f/permissions.tf`](./infra-test/multi-f/permissions.tf).
The condition's `backend_identity_user_name` must match the name generated by
`account-permissions` (`terraform-backend-${account_label}`). Its default now
matches that root's default account label; override it when using a different
label. The user ARN belongs in the condition, not in `Principal`.

## State and cost notes

- Each test scope has its own remote state key. Do not combine or reuse the
  state of independent roots.
- `backend-state/` uses local state because it creates the backend itself.
- AWS charges may apply. The `multi-f` scope avoids NAT gateways and paid
  interface endpoints, but Lambda, API Gateway, S3, CloudWatch Logs, and an
  optionally created Route 53 hosted zone can incur charges.
- S3 versioning can retain old object versions after overwrites. Remove test
  objects and review retained versions before destroying a test stack.
- Review IAM policies and trust conditions before using any configuration
  outside a disposable test environment.

See each directory's README for its inputs, resources, state configuration,
and stack-specific instructions.
